Given this, "kicked out"/"closing" was investigated **structurally**: what in the code could
plausibly produce exactly that symptom, with real numbers, not speculation.

### What the code rules out
- **Not a caught render error.** `src/app/_layout.tsx` wraps the entire app in one root
  `ErrorBoundary` (`src/components/error-boundary.tsx`). A render-phase crash shows a branded
  "Something went sideways — Try again" card, not a closed app — so if testers saw the app
  *disappear*, this is NOT that path, by design.
- **Not a global auth-state-driven redirect.** `subscribeToAuthChanges` (`auth-service.ts`) —
  the one function that could react to a session loss by navigating the user away — is
  **defined but never called anywhere in the app** (confirmed by a full-repo grep). Auth is
  anonymous-first (`signInAnonymously`, no login screen to get "kicked" back to); nothing
  currently force-navigates on a session event.
- **No obvious duplicate-fetch/infinite-refetch bug.** Reviewed every `useEffect`/
  `useFocusEffect` in `you.tsx`, `index.tsx`, `compare.tsx`, `explore.tsx`, `private.tsx` — all
  have stable `useCallback` dependencies; `you.tsx`'s `loadRemote`/`loadCommonality` re-running
  on every tab refocus (`useFocusEffect`) is a deliberate, commented data-freshness choice, not
  a bug, and explicitly preserves the last-good state on a transient failure rather than
  flashing an error over real data.

### The high-confidence finding: Creature compositing, decoded redundantly, in multiple places, at native-crash-causing memory cost
This matches **both** "closing unexpectedly/kicked out" (consistent with an iOS memory-pressure
jetsam, which a JS ErrorBoundary cannot catch or even see) **and** "slow" (real decode/CPU cost
repeated unnecessarily), with concrete numbers:

1. **The asset format itself is already known and flagged as the leading suspect — not newly
   discovered tonight.** `assets/creatures/` (131M) + `assets/relics/` (73M) = 204M of
   individual trait-layer files, each a large PNG **wrapped in a base64 data-URI inside an
   SVG**. Individual layer files run up to **7.4MB each** (`apparently_you_strong_wings.svg`).
   A full Creature composition stacks ~5 of these layers at once. Commit `96f6166` (2026-10-27,
   the session immediately before this one) already found this and says so directly in its own
   message: *"remains the strongest suspected contributor to both the slowness and the
   memory-pressure crash reports... locked pending explicit approval for any future change"*
   (per the earlier reversion in commit `c9a3ca8`). **This runbook's instruction not to reopen
   approved creative/architecture decisions means this format itself is not touched tonight** —
   but it is restated here, verified against the real file sizes, because it is still the
   single most important unresolved item for the owner's attention.
2. **New this session: the SAME full composition is very likely resident in memory multiple
   times simultaneously during completely ordinary navigation**, which compounds (1) rather
   than being a separate issue:
   - `CreatureStage` (Today tab, `src/app/(tabs)/index.tsx`) and `you.tsx` (You tab) both render
     the exact same `CreatureAvatar` component (`src/components/creature/creature-avatar.tsx`)
     — confirmed by reading both call sites. `CreatureAvatar` wraps `CreatureTestComposer`,
     which is the one real compositing implementation; there is no shared decode cache between
     call sites — each mount independently parses and rasterizes its own base64 SVG layers,
     **regardless of the `size` prop**, since react-native-svg scales the already-rasterized
     bitmap at render time, not before decoding it. A smaller on-screen preview costs exactly as
     much memory to decode as a large one.
   - The app's 5 tabs are built on `expo-router/unstable-native-tabs` (`src/components/app-
     tabs.tsx`) — a thin wrapper over iOS's native `UITabBarController`. Standard, expected
     native-tab behavior is that each tab's content, once visited, stays resident; iOS tab bars
     don't unmount a previously-visited tab's view just because another tab is selected. That
     is normal for light tab content — it is a real cost multiplier for a tab whose content is
     a multi-megabyte image decode.
   - `src/app/creature-read.tsx` (pushed via the Stack navigator from either tab) renders its
     own `CreatureAvatar` on top, and Stack navigators keep the screen underneath mounted (by
     design, for the back-swipe gesture) rather than unmounting it.
   - **Net effect:** a single, completely ordinary session — open the app (Today decodes one
     composition), tap to You (a second, independent decode of the same layers), tap into the
     Creature read/export screen (a third) — can hold **three independently-decoded multi-layer
     Creature compositions in memory at once**, on top of whatever Relic compositions (73M of
     assets, same format) are similarly resident from `RelicStage`/`relic-read.tsx`/`you.tsx`.
     This is exactly the kind of cumulative memory pressure that produces an iOS jetsam (app
     silently killed by the OS, no crash report the user ever sees, feels exactly like "the app
     closed and kicked me out") after "prolonged interaction," not necessarily on cold start —
     matching the owner's own description.
3. **One instance of this exact pattern was already found and fixed last session**
   (`creature-read.tsx`'s preview Modal no longer renders a second, redundant composition
   underneath itself while open — verified still in place this session, `hideAvatar` at
   `creature-read.tsx:325`). That fix is real and correct, but it only addressed the
   *within-one-screen* case, not the cross-tab/cross-navigation case documented above.

### Why no further code fix was made tonight
A correct, low-risk fix for item 2 would require either (a) a shared, cross-screen Creature/
Relic decode cache (a real, non-trivial architecture addition, risky to write and ship untested
on any device hours before release), or (b) changing how tabs/stack screens retain content
(risking other regressions in a native-tabs integration that already has its own documented
quirks — see `app-tabs.tsx`'s own comments about iOS tab-bar appearance bugs already fought
this engagement). Both are the "speculative architectural refactor" this runbook explicitly
says not to do. The actually-safe, non-architectural fix — collapsing the asset format itself
so a single decode is cheap enough that redundancy stops mattering — is the one already
explicitly locked pending the owner's own re-approval. **Recommendation, not a tonight-action:**
the owner should decide whether to re-approve a corrected version of the reverted PNG/format
work (the `_png_experiment` directory and `scripts/experiment-extract-embedded-png.ts` from
that attempt are still on disk, captured in the Phase 1 backup, available to resume from) —
this is the highest-leverage fix available for both the crash reports and the slowness, but it
is explicitly an architecture/content-pipeline decision, not an engineering judgment call to
make unilaterally tonight.

Not possible in this sandbox (no device, no profiler). This is marked explicitly, per this
phase's own PASS criteria, as **unverified — flagged for the owner's physical-device QA on
